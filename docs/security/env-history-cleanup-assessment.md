- GitHub 当前报告 0 个可见 fork，但这不能排除已经删除的 fork、私有副本、镜像、归档、CI 缓存、下载包或本地克隆。

- 即使主仓库不再从分支或标签引用旧对象，托管平台仍可能在一段时间内保留不可见对象；是否需要平台支持介入必须另行确认。

## 6. 两种处理方案对比

### 6.1 方案 A：不重写历史

措施：依靠已完成的凭据轮换、旧值撤销、停止跟踪、精确忽略规则、协作者通知，以及后续 Secret Scanning 和 Push Protection。

优点：

- 不改变任何提交 SHA、PR 引用或协作者分支关系。
- 不触发大范围重新克隆、自动化失效或部署意外。
- 已撤销的旧凭据不能继续用于认证，直接攻击价值显著降低。

缺点：

- 历史路径及其中可能存在的基础设施标识仍可被公开访问。
- 无法满足要求公开历史完全不含秘密材料的严格政策。
- 仍需持续监控旧账号、Provider Key 和 Token 是否确实失效。

### 6.2 方案 B：重写历史

措施：在隔离环境中从所有批准的引用移除 `.env` 历史，再经过验证和独立授权更新远端引用。

优点：

- 主仓库活跃引用不再指向包含 `.env` 的旧历史。
- 更符合禁止凭据文件进入版本历史的严格治理目标。

缺点：

- 受影响提交及所有后继提交 SHA 改变，PR、分支、链接和审计引用可能失效。
- 需要暂停推送、暂停自动化和部署、备份、演练、强制更新及全员重新克隆。
- 不能清除 fork、旧克隆、镜像、缓存或他人保存的副本。
- 操作失误可能造成分支丢失、旧历史重新进入主仓库或服务意外部署。

## 7. 推荐决策

在“所有实际使用凭据均已轮换并撤销旧值”、当前无可见 fork、无标签且仓库规模较小的已知条件下，建议：

1. **当前选择方案 A，不立即重写历史。**
2. 先完成 GitHub Secret Scanning、Push Protection、分支保护和部署密文复查。
3. 检查数据库、Provider 和管理接口的旧凭据拒绝记录及异常访问，但不得在仓库报告中记录凭据值。
4. 只有在合规政策明确要求、审计发现不可轮换敏感信息，或仓库所有者接受高操作风险时，才启动方案 B。
5. 方案 B 必须建立新的批次、规范计划 JSON 和 SHA-256，并为备份、演练、远端引用更新和每次 force push 分别授权。

## 8. 历史清理前置条件

进入任何执行批次前，必须全部满足：

- 仓库所有者和安全负责人书面批准清理范围。
- 再次确认所有实际使用凭据已轮换，旧凭据已撤销。
- 制作包含全部分支和标签的完整仓库备份，并验证恢复能力。
- 实时列出所有本地与远端分支、标签、PR、release、GitHub Actions、部署钩子、镜像和可见 fork。
- 协作者确认收到通知并在维护窗口暂停 push、merge 和发布。
- 暂停自动合并、GitHub Actions 定时任务和 Render 自动部署。
- 在与生产远端隔离的副本中演练，不读取或展示 `.env` 内容。
- 为旧引用、新引用和对象可达性设计只基于路径及提交关系的验证方法。
- 明确 GitHub 平台缓存、PR 内部引用和支持工单处理策略。
- 准备协作者重新克隆说明，禁止从旧克隆恢复分支。

建议为该小型仓库预留至少一个 2–4 小时的停止写入维护窗口，并保持写入冻结，直到远端验证、自动化验证和协作者重新克隆通知全部完成。具体时长必须由仓库所有者根据协作者数量、部署依赖和平台响应重新评估。

## 9. 恢复原则

- 历史清理前的完整备份是唯一可信恢复基线；仅保留本地 reflog 不构成完整备份。
- 演练失败时直接废弃隔离副本，不触碰生产远端。
- 远端更新开始后如验证失败，应停止所有后续引用更新，保持写入冻结，并由仓库所有者决定是否恢复旧引用。
- 恢复旧引用本身会重新公开旧历史，必须经过单独授权和风险确认。
- 不得自动删除备份、旧分支或标签；保留期限由安全负责人确定。
- 不使用 `reset --hard`、自动清理或未经授权的强制更新作为恢复手段。
